# LexisGraph 内部系统功能对照与实施方案

本方案依据 2026-10-14 对已登录 MARKUP 的页面检查及其官方操作指南修订。替代上一版规划中对产品功能范围的判断；上一版已经实现的上传、原文保护、修订与恢复能力继续保留。

实施更新：2026-10-14 已交付第一版功能闭环，包含 SQLite 长期记录、审查条件、清单维护与版本快照、文字对比与可选模型分析、Word 交付、起草阶段与单条追问。实际使用步骤及本版边界见 [内部系统使用说明](内部系统使用说明.md)。本版保持单实例，不包含社区或商业入口；模型相关能力需要可用配置。

## 1. 产品边界

内部合同工作系统。保留现有蓝白灰风格和三栏 workbench，不改成营销网站或聊天首页。

纳入：任务入口、合同审查、审查记录、企业审查清单、合同起草、起草记录、模型配置、必要的内部操作说明。

不纳入：社区、商业升级、套餐额度、开票、推广、联系我们、小程序、外部会员体系。Word 插件暂不建设，先完成网页端审查和交付。

## 2. 已核实的参考能力与当前差距

“页面”表示已登录界面可见；“指南”表示官方文档明确描述，但本次没有执行该业务流程。内部设计列为本系统拟实现的能力，不代表现有代码已经具备。

| 能力 | 核实来源 | 当前系统 | 内部设计 |
| --- | --- | --- | --- |
| 审查记录 | 页面：文件名称、任务类型、审查时间、状态 | 仅恢复当前浏览器会话的一份合同 | 长期保存多份任务，打开历史结果，继续修订 |
| 审查模式 | 页面：快速、深度、清单、对比四种 | 一条审查流程 | 各模式具有实际不同输入和处理流程 |
| 审查立场和尺度 | 指南：立场与强势/中立/弱势尺度分开设置 | 仅甲乙方/中立立场 | 分开配置我方主体和谈判尺度 |
| 交易背景 | 指南：审查前补充背景 | 无背景输入 | 业务目的、交易背景、重点要求可填写并参与分析 |
| 企业审查清单 | 页面有管理入口；指南说明导入、解析、选择、编辑 | 提交前检查说明弹窗 | 可创建和维护规则条目，冻结本次使用版本并逐项审查 |
| 对比审查 | 页面说明和指南：待审合同与参考合同 | 无 | 两份合同输入，识别新增、删除、变更，并评估风险 |
| 参考资料 | 页面入口；指南说明关联材料参与深度审查 | 无 | 附件提取、核对、选择使用，并记录实际使用范围 |
| 单条意见追问 | 指南：针对原文/修订建议继续对话 | 无 | 卡片内展开追问，生成新的建议供人工采纳 |
| 批注与在线修改 | 指南：原文定位、编辑、批注 | 正文整体编辑，尚无条款批注 | 条款备注、处理意见、人工修改与版本记录 |
| Word 交付 | 指南：当前合同、全部建议、意见书等导出范围 | TXT 修订稿、浏览器打印意见书 | DOCX 合同和意见书，明确导出范围和修订痕迹 |
| 合同起草 | 页面有背景输入；指南含背景确认、大纲、成稿 | 无 | 需求 → 背景确认 → 大纲确认 → 成稿编辑 → 导出/审查 |
| 起草记录 | 页面：文件名称、起草时间、状态 | 无 | 保存背景、大纲和草稿版本，可中断后继续 |

本次参考账号为体验版，清单创建、参考资料与部分审查模式受版本限制；审查记录和起草记录尚无可打开的业务条目。没有将指南描述视为已在该账号完整实测，也没有验证原站输出质量或其 Word 排版保真效果。

## 3. 主页与导航

侧栏固定为：

1. 开始
2. 审查记录
3. 审查清单
4. 合同起草
5. 起草记录

模型配置放在顶栏，内部操作说明放在侧栏底部的小入口。企业模板从起草流程选用，不再堆一套重复的导航。

“开始”页面仍使用现有中央卡片，卡片分为以下层次：

- **任务选择**：快速审查、深度审查、清单审查、对比审查。
- **正文输入**：上传/粘贴。示例保留为辅助入口。
- **必要条件**：名称、类型、我方主体、审查尺度；清单模式必须选用清单，对比模式必须提供参考合同。
- **补充条件**：交易背景、重点要求、参考资料按需展开。
- **开始任务**：创建持久化任务、进入 workbench，再核对并发起审查。
- **最近工作**：显示真实最近任务、状态及更新时间。无数据时展示空状态，不填虚构统计数字。

避免一个表单同时展开所有条件。切换模式时保留已输入的正文，切换来源时保留各自草稿；发起任务时明确实际采用的模式和材料。

## 4. 四种审查必须有实质差别

### 快速审查

正文与基本立场输入，执行约定范围的基础检查，优先提供关键风险及定位。记录具体检查范围和结果来源，不能宣称已经完成全面深度审查。

### 深度审查

允许交易背景、审查尺度和参考资料；分析完整合同，覆盖条款之间的关联，并输出修订与行动建议。材料过长时分段处理并记录覆盖范围，不得只截取前几个条款而宣称完成全案分析。

### 清单审查

读取选定企业清单的固定版本，每个条目输出：通过、未通过、待人工确认或不适用；关联原文、核验依据、问题说明和修订建议。未通过与待确认必须区分。

清单应支持名称、适用合同类型、检查项、判断要求、风险等级和参考条款。支持手动维护与从文件提取草稿；导入后先人工核对，发布后才能用于任务。修改清单不回写历史审查结果。

### 对比审查

待审合同与参考合同分开保存，先定位文字与条款差异，再判断变更带来的风险。删除条款在参考合同中仍可查看；相似文字匹配有歧义时显示待确认，不直接定位或替换错误条款。

参考模板存在的条款并不自动等同于企业标准；企业底线需要显式配置。

## 5. Workbench 的合理增量

保持左栏检查概览、中栏合同、右栏意见卡片。新增内容沿用现有卡片、按钮和字号体系。

| 区域 | 调整 |
| --- | --- |
| 顶栏 | 展示任务名、审查模式与版本；保留开始/重新审查；增加保存状态与导出菜单 |
| 左栏 | 按模式显示概览。清单模式显示通过/未通过/待确认数量和条目；对比模式显示新增/删除/修改数量。财税检查仅在相关任务中展开 |
| 中栏 | 保留原文和已采纳修订稿；增加条款级编辑、批注。对比模式提供参考合同与待审合同的差异视图 |
| 右栏 | 保留定位、依据、修订对照、采纳与撤销；增加待处理/已采纳/不采纳/待复核状态，以及条目内追问和备注 |
| 导出 | 当前编辑稿、全部建议稿、全部意见书、仅已采纳意见书分开选择；选择全部建议时明确其内容不同于当前编辑稿 |

追问不把整个 workbench 替换成聊天页面。点击单条意见后在该卡片中展开；新的模型回答不自动覆盖合同，仍需用户核对并采纳。

评分属于某次审查的原文版本。采纳建议、人工编辑、切换立场或尺度后，不能把旧分数显示为新稿质量结论。重新审查产生新版本，历史版本保留。

## 6. 记录与持久化

服务端持久化是下一阶段前提，会话存储只继续承担临时输入和当前页面状态。

初期使用 SQLite 与本地文件目录即可，沿用当前 FastAPI 项目，无须为了功能补齐重写前端框架。

- **案件**：名称、类型、创建/更新时间、当前版本。
- **审查任务**：模式、合同版本、立场、尺度、背景、参考资料、清单版本、运行状态、结果来源。
- **任务结果**：风险/清单/差异条目、审查快照、执行记录。
- **人工处理**：采纳、不采纳、撤销、备注、复核状态，与具体任务和原文版本关联。
- **清单版本**：发布内容固定，后续修改形成新版本。
- **起草任务**：背景确认内容、大纲、正文版本及每阶段状态。

审查记录页支持名称搜索、模式和状态筛选、日期筛选、打开结果、从已有版本再审查。采用可恢复的归档功能管理过期记录。

必须区分“正在运行”和“已完成待复核”。应用重启后遗留的运行中任务标为中断并允许重试，不能永久显示正在审查。

当前尚无内部身份接入；初期按单个内部实例设计。负责人、审批流和权限模型待确定真实使用者后增加，不预先制造组织和团队功能。

## 7. 合同起草

起草独立页面复用整体视觉风格，不挤进审查 workbench 的现有三栏。

1. 描述起草需求，可选企业模板、参考资料。
2. 提取待确认交易信息：主体、标的、价款、交付、验收、付款、期限及特殊要求。缺失信息保留为待填写项。
3. 生成并确认条款大纲，允许调整条目。
4. 按已确认信息生成正文，允许编辑和定向重写。
5. 保存草稿、导出 DOCX，或把该草稿版本送入审查。

模型未配置或调用失败时明确提示，保留输入与已确认大纲。模板填充与模型生成分别标识，不用示例合同冒充根据交易背景生成的结果。

## 8. 实施顺序和验收

### 第一批：长期任务与审查条件

服务端存储 → 审查记录 → 首页任务入口 → 交易背景与尺度 → workbench 关联任务版本。

验收：上传两份不同合同，完成审查并分别处理意见；关闭浏览器、重启服务后，两份记录及处理状态仍可正确打开。新版本审查不会覆盖旧结果。背景和尺度实际进入审查请求与处理逻辑。

### 第二批：企业清单与逐项结果

清单管理 → 导入核对与版本发布 → 首页选用 → workbench 逐项状态与定位。

验收：自建包含三项要求的清单，审查能分别输出三项结果；缺失条款明确指出，无法判断的条目进入待确认；修改企业清单不会改变此前任务的记录。

### 第三批：Word 交付、批注与对比

DOCX 交付与导出范围 → 条款备注和处理状态 → 对比审查 → 深度审查参考资料。

验收：采纳一项、拒绝一项、增加人工备注，导出的当前合同和意见书准确对应处理范围；使用只修改一个付款条款的两份合同，能定位实际差异，其他条款不会被误报成全部变更。Word 排版保留与修订痕迹需要独立视觉验收。

### 第四批：起草与单条追问

背景确认 → 大纲确认 → 合同生成 → 起草记录 → 送审；再增加工作台单条追问。

验收：起草到大纲阶段退出，重新打开能继续；未提供的金额不会被编造；生成草稿能独立保存、导出与送审。单条追问产生的替代建议需人工采纳才能改变合同。

不将未实现模式做成能点击却没有业务行为的正式入口。每批完成后交付可用闭环，再扩大功能。
