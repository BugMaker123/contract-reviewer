# 技术架构与应用优化修复建议

扫描日期：2026-10-19。范围：当前工作区的 FastAPI 后端、Vue 前端、SQLite 存储、后台任务、文件导入导出与测试配置。

本文是修复规划，未修改业务代码。代码位置以本次扫描版本为准。区分直接可见的实现缺陷、故障窗口与扩展部署限制；没有把推断风险写成已发生事故。未调用真实模型、未进行破坏性压力测试，也未核验法律内容的正确性。

## 1. 总体判断

当前适合继续按“本机、单进程、内部工具”维护。已有审查输入快照、乐观锁、原文定位校验、人工核验、后台执行及浏览器回归基础，无需立即拆微服务或替换全部存储。

优先修复状态一致性和模型凭据边界，再完善资源限制、发布及数据恢复。若扩展为多人共享服务，身份权限与任务执行协调必须先完成。

优先级定义：P0 为可能造成密钥泄露或严重访问越界的问题；P1 为业务一致性、数据可靠性及明显资源风险；P2 为维护性、规模化与使用体验改进。P0 的实际暴露程度取决于是否配置服务端密钥、是否允许其他进程或用户访问接口。

## 3. 逐项修复建议

### A01：模型地址与服务端密钥必须绑定

**位置**：`backend/graph.py:156` 的 `resolved_api_key()`、`:160` 的 `get_llm_client()`；`backend/models.py:4`；`backend/main.py:170` 的模型连接测试。

**问题**：请求可以指定 `base_url`；当请求没有 API Key 时，后端自动读取 `DEEPSEEK_API_KEY` 或 `OPENAI_API_KEY`。因此，自定义地址可能收到服务端密钥；接口同时具备从服务器向请求指定地址发起连接的能力。CORS 不承担接口鉴权，也不能约束非浏览器调用方。

**修复**：服务端配置 provider ID、固定地址和凭据的映射，请求只选择 provider ID。保留用户自定义地址时，要求使用用户明确提供的密钥，禁止回落到环境密钥。共享部署限制协议、主机、端口、重定向及解析后的目标地址；企业内网模型用显式允许列表配置。连接错误返回分类消息，不直接回传第三方异常全文。

**验收**：用 mock 客户端断言“自定义地址 + 空密钥”不会获得环境密钥；测试所有模型入口，而非只测试连接检查。覆盖不允许的地址和重定向；测试不得使用真实凭据。

### A02：排队期间仍可编辑上一轮修订

**位置**：`backend/revisions.py:56` 的 `editable_run()`；`backend/revision_api.py` 的重生成、编辑和恢复入口。

**问题**：`editable_run()` 只拒绝任务 `status == 'running'`，没有拒绝 `queued`。新一轮排队时，任务的 `active_run` 仍可能指向上一轮已完成运行；输入未改变时，上轮结果满足其余校验，因而可以继续修订。`save_handling()` 已同时拦截两种状态，业务规则不一致。

**修复**：统一状态谓词，禁止 `running/queued` 期间修改当前处理结果；最终写入时在同一事务中复核 task 状态、active_run 和 run revision。前端按钮按相同规则禁用。

**验收**：填满队列后让同一任务重审进入 queued，分别调用手改、恢复、AI 重生成、当前稿核验和追问；应拒绝不允许的操作，并保持历史及新快照不变。

### A03：跨对象业务提交不是原子操作

**位置**：`backend/review_jobs.py:54`、`:78`、`:85`、`:93`；`backend/workspace_api.py:350`、`:388`；`backend/revisions.py:106`。已有可参考实现：`backend/store.py:179` 的 `complete_review()`。

**问题**：更新 run 后再独立更新 task。第二次写入失败时可能出现“run 已完成，task 仍运行”或“修订已保存，task 仍完成”。取消与失败分支也有相同窗口。部分流程先校验 task 再只对 run 加乐观锁，无法阻止两次操作间 task 状态变化。

**修复**：在 Repository 增加完成、失败、取消、处理意见和保存修订等业务事务；事务内校验状态及两方版本，统一更新。任务完成事件只在事务提交后发布。异常处理应保留原始异常，避免数据库故障引发二次异常掩盖原因。

**验收**：对第二次写入注入失败，验证整体回滚；并发执行开始审查和保存修订，确保只允许合法顺序；重新打开任务后状态与当前运行一致。

### A04：分类与清单缺少数据库级业务约束

**位置**：`backend/workspace_api.py:464` 的 `category_data()`、`:503` 的 `validate_category()`、`:532` 的版本保存；`backend/store.py:23` 的通用 objects 表。

**问题**：分类名称/编码通过先遍历再写入保证唯一；并发请求可能均通过。清单创建先检查分类存在、之后另开事务写入，分类在此期间可能被删除。清单历史版本创建和当前版本更新也不是一个事务，冲突可能留下多余历史记录。

**修复**：先以事务封装校验与写入，并为分类名称、编码增加适当的唯一索引。明确名称大小写和空白归一化规则。分类与清单若继续用 JSON 存储，关联检查和删除必须共享事务；中期可拆为有外键的独立表。清单版本与当前版本一起提交。

**验收**：并发创建同名分类只成功一次；并发删分类/建清单不产生悬空关联；清单冲突不新增伪历史版本。

### A05：原始文件生命周期与数据库脱节

**位置**：`backend/main.py:94`、`:112`；`backend/workspace_api.py:277` 的采纳稿转新源文件；`backend/word_export.py:13`。

**问题**：先创建 source 记录，再写文件，磁盘失败后留下无文件记录。采纳稿在 `start_run()` 校验之前落盘，随后版本冲突会留下未引用文件。数据库路径支持 `LEXIS_DB_PATH`，源文件目录却固定在项目 data 下，部署和备份路径容易错配。当前归档不是彻底删除，未见统一孤儿清理及保留期限机制。

**修复**：统一数据根目录配置；文件先写临时路径并计算校验值，再通过明确的 pending/ready 状态及原子重命名发布，失败补偿并在启动时对账。清理必须检查任务、运行快照及其他源记录引用。定义保留、彻底删除和恢复策略；备份同时覆盖数据库和对应文件，并提供恢复校验命令。

**验收**：模拟磁盘满、版本冲突、写入中断；不能产生可用但缺文件的 source。恢复备份后验证文件哈希及 Word 导出；自定义数据目录下不向默认目录写文件。

### A06：导入和进度落库阻塞异步请求

**位置**：`backend/main.py:55` 的异步导入函数内直接执行 DOCX/PDF 解析；`backend/review_jobs.py:54`、`:70` 的同步 repo 调用；`backend/store.py:33` 的 SQLite 连接允许等待 15 秒。

**问题**：同步 CPU/磁盘操作运行在事件循环上，较慢解析或数据库锁等待可能拖慢其他请求、SSE 心跳与取消响应。10 MB 上传限制在应用读取阶段检查；解压体积、PDF 页数和解析耗时没有相应预算，正文长度是在解析完成后检查。

**修复**：解析移入有并发上限的工作线程；需要强制终止的解析任务使用进程隔离。增加 DOCX ZIP 条目数、解压总量、压缩比、PDF 页数与解析时间限制；入口层限制请求体。数据库采用受控写入线程或异步访问适配；评估 WAL，避免直接改为“所有写入无限并发”。

**验收**：用大文件、锁等待、异常压缩文件测试，同时请求轻量接口和取消任务；在预先定义的延迟预算内响应，超限文件返回明确错误。

### A07：本地队列不具备全局背压和多进程协调

**位置**：`backend/review_queue.py` 的 `LocalReviewQueue`、`credential_group()`；`backend/review_jobs.py:13`；`backend/main.py` lifespan 的 `interrupt_running()`。

**问题**：每个凭据分组最多五个任务，但分组数和等待任务数无限制；换不同凭据可扩大总体并发。凭据仅存任务闭包，进程停止后不能继续执行，当前设计会将未完成记录标记中断。多个进程各有队列和 `_jobs`；任一新进程启动还会对共享数据库运行恢复逻辑，可能干扰其他进程。

**修复**：短期明确仅支持一个 worker，加全局执行上限、队列长度、等待时限和 429/503 反馈。辅助模型功能也纳入同一资源调度策略。多人部署时再引入独立 worker、持久任务、租约/心跳与幂等终态提交；恢复只能处理确认失联的所有者。凭据通过受控 provider 引用获取。

**验收**：不同凭据的总体并发不超限；满队列立即反馈；取消释放容量。多进程方案必须验证启动、重启与订阅路由，不得只把 uvicorn workers 改大。

### A08：字符数上限不能代替模型上下文管理

**位置**：`backend/workspace_models.py` 的 TaskInput；`backend/graph.py:542` 的全文 prompt；`backend/workspace_review.py:14`；`backend/review_progress.py` 的 360 秒总等待；`backend/workspace_api.py:543` 的追问。

**问题**：合同允许 20 万字符、参考资料 5 万字符，清单、要求和历史内容还会继续加入 prompt。没有按模型估计 token 和预留输出预算；多个核验阶段与重试累计后可能超时。当前已有截断输出检测和六分钟等待上限，这些措施不能解决请求前的容量匹配问题。

**修复**：集中管理模型能力、上下文和输出预算；超限时按条款分块，保留稳定位置与覆盖台账，再进行跨条款汇总。追问仅发送相关上下文；为阶段分配时间/费用预算，并在调用前告知无法完整执行的范围。禁止静默截断合同后显示全文审查。

**验收**：长合同跨越上下文阈值时明确拒绝或完整分块；首尾条款均有覆盖记录；模型重试耗尽时保留可解释的阶段及错误分类。

### A09：多人共享之前补齐身份和资源归属

**位置**：`backend/main.py` 的应用挂载；`backend/workspace_api.py` 各资源路由；`run.py` 当前绑定 `127.0.0.1`。README 已明确尚未接入账号权限。

**问题**：接口未校验调用身份，拿到记录 ID 即可访问相应合同、源文件、运行结果及导出；记录没有组织/所有者隔离。对当前本机工具这是已知边界，不能据此直接宣传多人可用。

**修复**：共享部署接入组织身份、会话和资源归属；读写、SSE、文件和导出一并授权。区分管理员、审查人、只读者；审计记录操作者和时间。继续保持本机模式时至少明确允许的 Host/Origin 与本地接口访问边界。

**验收**：不同用户或组织不能通过替换 ID 读取、修改、订阅或导出对方资源；组织间清单版本与分类隔离。

### A10：浏览器凭据保留时间过长

**位置**：`frontend/src/portal/features/model.js:5`；`frontend/src/composables/useWorkbench.js:1037`；两个入口均读取 `LEXIS_API_KEY`。

**问题**：密钥以明文长期保存在 localStorage，同源脚本和浏览器配置访问者可读取；退出应用没有统一清理流程。“不写案件数据库”并不等于没有持久保存。

**修复**：优先采用服务端 provider；用户临时密钥默认只保存在内存，持久记住作为明确选项，提供清除入口及保留范围说明。集中配置读写，避免首页和工作台默认模型不同、参数保存不一致。

**验收**：默认使用后 localStorage 无密钥；清除配置同时清理所有入口；首页与工作台显示同一模型及重试设置。

### A11：进度事件和审查快照造成数据放大

**位置**：`backend/review_jobs.py:26`、`:36`、`:70`；`backend/store.py:165`；`backend/review_progress.py` 的未限定容量 asyncio.Queue。

**问题**：每个事件保留在内存，轨迹每次累积后写回；Repository 更新会重新读取和序列化整个 run JSON，包括输入及已有结果。完成订阅仅在后续 launch 且数量超过阈值时清理，且单任务事件没有容量限制。慢消费者与大量进度容易放大内存、数据库写入及 SSE 重放成本。

**修复**：对进度节流合并；独立追加事件表，业务快照只存结果及关键状态。内存使用容量和时间双限制；终态按 TTL 回收。SSE 使用单调事件 ID、游标续传或明确发送终态快照。

**验收**：记录长任务和多任务的事件数、数据库增长及内存峰值；停止产生任务后缓存仍按时回收；重连不会重复应用处理结果。

### A12：分页之外仍有全量读取路径

**位置**：`backend/workspace_api.py:215` 的报表、`:247` 的任务详情、`:458` 与 `:509` 的无 page 分支；`backend/store.py` 的 `list()`。

**问题**：任务列表分页已实现，但任务详情为取得历史版本摘要仍先加载所有 run 完整 JSON；分类/清单兼容接口可返回全量正文；报表 fetchall 后在 Python 聚合。数据增长时响应体、反序列化和内存会成为瓶颈。

**修复**：新增运行摘要查询与历史分页；清单选择只取摘要，详情按需读取；报表 SQL 聚合并支持日期范围、分页和流式 CSV。检查实际查询计划后再决定表达式索引或关系表迁移。

**验收**：准备含长合同、多版本和大量清单的数据，衡量响应体、P95 延迟及峰值内存；列表和摘要响应不含合同正文、完整意见及清单条目。

### A13：开发启动方式兼作发布流程

**位置**：`requirements.txt`、`requirements-dev.txt`、`run.py`、`backend/frontend_build.py`、`frontend/package.json`；仓库未见 `.github` 工作流。

**问题**：Python 依赖仅设下限，环境重建可能解析到不同组合；启动器按需联网安装/构建前端，发现 vite 目录后不会基于锁文件变化自动重装依赖。`reload=True` 适合开发，代码变化会重启并中断任务。前端已有 package-lock，应保留。

**修复**：锁定经验证的 Python 依赖并声明 Python/Node 版本；分离开发入口与单 worker 发布入口。安装及构建在发布前完成，发布产物记录版本。增加自动检查：依赖安装、pytest、前端构建、关键浏览器流程；故障保留截图/日志并脱敏。

**验收**：全新环境按锁文件构建且测试通过；发布服务启动无需 npm 下载；开发与发布行为有清晰说明。补充健康检查、请求关联 ID 和结构化错误日志，便于定位任务失败。

### A14：刷新和关闭页面可能丢失最近修改

**位置**：`frontend/src/composables/useWorkspace.js:164` 的 600 ms 防抖；`frontend/src/composables/useWorkbench.js:1340` 附近的路由离开守卫。

**问题**：站内路由已有等待 flush 的守卫，应保留；但浏览器刷新、关闭或崩溃不经过 Vue 路由守卫，最近的防抖修改及在途保存可能丢失。现有页面会话草稿不能直接视为工作台修改的可靠恢复机制。

**修复**：跟踪 dirty/保存中状态，必要时注册 beforeunload 提示；对合同敏感内容明确是否允许本地恢复草稿及何时清除。可以尝试页面隐藏时保存，但不能依赖卸载阶段异步请求保证成功。刷新后显示未保存草稿与服务器版本差异，避免自动覆盖。

**验收**：输入后立即刷新、断网关闭及保存冲突时，不错误显示已保存；有可理解的提示或恢复入口。正常站内跳转仍等待保存。

### A15：模块边界需要按职责收敛

**位置**：`backend/workspace_api.py` 同时承担 CRUD、审查编排、报表及 Word 内容构建；`backend/graph.py` 混合规则、模型客户端、prompt 与图节点；`frontend/src/composables/useWorkbench.js` 约 49 KB。

**问题**：改动状态、模型或导出功能会触及大型模块，容易出现 A02 一类规则分叉；前端 API、模型配置和错误处理分散，后续排障与功能迭代成本较高。
