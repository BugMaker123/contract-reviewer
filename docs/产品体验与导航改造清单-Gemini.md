# LexisGraph 产品体验与导航改造清单

审阅日期：2026-10-22。用途：交给 Gemini 进行交互设计与前端改造。

## 1. 结论与审阅范围

当前系统的主要问题是：功能按模块建设得比较完整，但用户完成一件事所经过的页面，没有遵循同一套导航、状态与操作规则。用户容易知道“这个页面能干什么”，却不容易知道“我从哪里来、下一步做什么、返回后会到哪里”。

建议保留现有蓝白灰方向、合同正文中心布局、三栏审查、列表管理和已有业务能力。优先修复流程连续性，再统一组件和视觉，不需要推翻重做。

本报告基于当前工作区前端源码、路由、状态保存和 README 审阅，包含尚未提交的工作区版本；未进行浏览器实测或用户访谈。因此，下文区分代码已确认的行为与需要实测的体验风险，不声称已验证屏幕效果、实际丢失数据或所有设备兼容性。仅新增本文档，不修改现有页面。

已有值得保留的基础：工作台有保存和离开保护；起草正文离开时尝试保存；AI 审查表单有 sessionStorage 草稿；部分列表有 KeepAlive 和滚动恢复；核验历史报告有记录 ID；历史审查与当前稿已做区分。改造应统一这些机制，而不是重新制造一套不兼容的状态系统。

## 2. 已确认的问题与修复方向

| 优先级 | 当前行为与证据 | 用户受到的影响 | 修复方向 |
|---|---|---|---|
| P0 | `StartReview.vue` 的 choose / ai / template / result 由局部 stage 控制，通常共用 `/`；只对 checklist 参数做特殊处理 | 视觉上换了页面，但浏览器没有相应步骤历史；刷新重新初始化 stage，难以回到同一报告 | 有独立任务含义的页面进入路由；已有核验结果以记录 ID 打开 |
| P0 | `WorkbenchSession.vue` 品牌和“返回主页”均调用 `leaveFor('/')`，没有按进入来源返回 | 从记录、起草进入工作台，退出却落到开始页，打断工作链 | 明确“返回审查记录”或“返回合同草稿”；缺少有效来源时回记录列表 |
| P0 | `PortalLayout.vue` 在模板配置时隐藏侧栏，仍只给“返回主页”；`TemplateReview.vue` 没有对应的返回模板列表入口 | 用户进入模板维护后失去所在模块和父列表的线索 | 专注模式保留统一顶部及“返回合同模板”，显示模板名和版本 |
| P0 | `ContractDrafting.vue` 的 dirty 只覆盖已生成草稿的标题与正文；briefChanged 虽存在，但离开与刷新保护未覆盖未生成需求及需求修改 | 填了一半的起草需求没有与正文同等的恢复保证 | 分开保存“起草需求草稿”和“合同正文草稿”，统一展示保存状态；实测刷新、缓存淘汰 |
| P1 | 核验记录页“新建审查”链接到 `/`，用户必须重新选择模式 | 已明确上下文的动作仍要求重复决策 | 改成“新建模板核验”，直接进入核验准备页 |
| P1 | “模板核验”既指模板填写区域/规则的人工确认，也指实际合同与模板的比对 | 用户分不清自己正在维护规则还是检查合同 | 前者统一叫“模板规则配置”，后者叫“合同模板核验” |
| P1 | `ContractTemplates.vue` 点击 DOCX 名称进入规则配置，点击其他格式名称打开预览 | 同一种点击操作根据格式产生不同结果，预期不稳定 | 名称统一进入详情/预览；独立按钮负责“配置规则”，非 DOCX 说明不支持规则配置 |
| P1 | `ContractDrafting.vue` 同屏有“返回起草列表”和“返回列表”两处等价入口 | 页面标题区域冗余，主任务焦点被分散 | 保留一个明确返回入口，标题右侧只放当前任务动作 |
| P1 | 工作台同时提供重新审查、保存、完成审核、意见书、导出，重新审查持续使用明显蓝色强调 | 已有结果时，视觉重心仍容易落在重新运行，处理和交付步骤不够突出 | 根据状态切换主操作，并展示完成/导出的前置条件 |
| P1 | `TemplateValidationRecords.vue` 将 TRUE/FALSE 置于结果显示中，同时另有 needs_review / incomplete 等详细状态 | 技术布尔值压过业务结论，“无法完整检查”容易被理解成已明确违规 | 主标签展示“符合规则 / 需修改 / 需人工确认 / 检查不完整”，保留原始字段供详情查看 |
| P1 | 列表状态多为组件内 ref；KeepAlive 有容量上限；核验详情关闭固定 push 到裸列表地址 | 同会话缓存可能正常，但刷新、直达、缓存淘汰后恢复缺少统一契约；关闭详情会增加一条历史 | 查询条件与页码可恢复；明确定义关闭、返回、浏览器后退的历史行为 |
| P2 | 入口页有紫蓝渐变、大圆角、悬浮位移，规则配置与表格采用更紧凑的工具风格；图标混有 SVG 和字符 | 页面虽各自完整，跨页时产品气质与密度变化明显 | 共用字体、颜色、圆角、间距与图标规范，允许工作台保留更紧凑密度 |
| P2 | `PortalLayout.vue` 最近工作区被 `v-if="false"` 隐藏 | 开始页主要服务新建，继续已有工作的路径不够直接 | 优先在“新建审查”页提供少量最近任务，不急于新增复杂首页 |

这里不建议把所有界面都做成相同密度：列表负责找对象，准备页负责输入，工作台负责长时间阅读和处理。应统一操作规则，保留场景差异。

## 3. 信息架构：先做小范围调整

第一阶段保留现有模块和 URL 兼容，不合并后台数据模型，不额外引入审批或组织权限。

建议侧栏：

```text
合同工作
  新建审查（原“开始”，包含风险审查与模板核验入口）
  审查记录
  模板核验记录
  合同起草

标准与资料
  合同模板
  审查清单
  业务分类

全局工具
  帮助、模型配置（保持稳定位置，弱化视觉权重）
```

核验记录属于工作结果，模板库属于规则资产，二者可以关联，但不应仅因为都含“模板”就放在同一业务层级。普通审查人员与规则维护人员目前没有权限区分，可先用导航分组表达任务差异。

暂不建设“统一合同中心”、大量统计卡片或新的仪表盘；这些会增加数据关联和迁移成本，不能直接解决返回问题。

## 4. 导航契约：先定规则，再画页面

### 4.1 四种行为必须区分

- **全局导航**：去其他模块；名称说明目的地，应用统一离开保护。
- **页面返回**：回明确的来源页面或父列表；按钮写“返回审查记录”“返回合同草稿”，避免笼统“返回”。
- **流程上一步**：回到当前准备流程上一步，保留已填内容，不退出模块。
- **关闭弹窗/抽屉**：回到背景页面原位置，恢复触发按钮焦点，不意外导航。

浏览器后退应遵循实际历史；应用返回不应一律调用 `router.back()`，否则从外部直达时可能离开应用。品牌点击作为全局导航单独定义，不冒充上下文返回。

### 4.2 路由建议

以下为目标方案，不要求一次性修改全部旧地址。

| 页面 | 建议地址 | 必须承载的信息 |
|---|---|---|
| 新建方式选择 | `/` | 两类审查的适用范围、继续已有工作 |
| 风险审查准备 | `/reviews/new` | 输入草稿标识、清单预选参数 |
| 模板核验准备 | `/template-checks/new` | 选中模板/版本、输入草稿标识 |
| 核验报告 | `/validation-records/:id` | 持久化核验记录 ID |
| 审查工作台 | 先保留 `/workbench?task=...&run=...` | task/run、来源上下文 |
| 模板规则配置 | 先保留 `/templates/:id/review` | 模板 ID、版本；更新页面文案即可 |
| 起草编辑 | 保留 `/drafting/:id/edit` | 草稿 ID、保存状态 |

兼容旧的 `/?checklist=...`、`/validation-records?validation=...` 及已有 task/run 链接，必要时用 replace 重定向。URL 只保存标识与可分享的界面参数，不放合同正文、凭据或背景资料全文。

### 4.3 来源与返回矩阵

| 从哪里进入 | 去哪里 | 应用返回动作 | 必须恢复 |
|---|---|---|---|
| 审查记录筛选后的第 3 页 | 工作台 | 返回审查记录 | 筛选、页码、滚动位置、原记录定位 |
| 合同草稿 | 工作台 | 返回合同草稿 | 原草稿 ID 与已保存正文 |
| 新建风险审查 | 新任务工作台 | 返回审查记录 | 已创建任务可找到；不返回已消费的空表单 |
| 模板列表 | 规则配置 | 返回合同模板 | 分组、查询、页码、原模板定位 |
| 模板核验准备 | 报告 | 返回核验准备 | 模板及文档引用；另提供“查看核验记录” |
| 核验记录 | 报告 | 返回核验记录 | 筛选与列表位置 |
| 外部链接/刷新直达工作台 | 工作台 | 返回审查记录 | 不依赖上一页存在 |
| 外部链接/刷新直达报告 | 报告 | 返回核验记录 | 直接读取记录，缺失时给可恢复错误 |

来源只接受站内允许的路由。可用 history state 加 sessionStorage 保存来源与列表快照；缺失时采用表中兜底。来源上下文按当前历史条目或会话隔离，避免一个全局 returnTo 被不同任务覆盖。

历史约定：进入独立详情一般 push；创建成功后用 replace 替换已消费的提交页面，避免后退重复提交；筛选输入变化通常 replace；应用返回若上一条确为来源可 back，否则 replace 到来源/父列表，避免“列表→详情→列表→后退又进详情”的循环。具体实现要同时验证浏览器前进和后退。

## 5. 三条核心流程的改造

### 5.1 风险审查：准备 → 执行 → 处理 → 交付

准备页按用户任务顺序排列：合同文档及名称 → 我方立场 → 审查要求 → 可选背景与参考资料。不要在上传合同之前堆满复杂参数。

“审查要求来源”使用业务语言：“通用审查 + 自定义要求”与“按企业审查清单”。`Prompt` 等实现术语放帮助文字，不放主选项名。公司制度确认、要求冲突等现有规则必须保留。

准备页底部固定显示就绪状态和一个主按钮。当前代码的 createTask 只创建任务并进入工作台，因此如果不改变执行逻辑，按钮应叫“创建任务并进入审查”；只有真正启动审查时才叫“开始审查”。不要仅靠改文案制造已运行的错觉。

工作台保留三栏：左侧导航/概览，中间正文，右侧当前意见。顶部统一为“返回来源 + 合同名称 + 状态/保存提示”，业务操作放一条工具栏。

| 当前状态 | 主操作 | 其他动作和反馈 |
|---|---|---|
| 待审查 | 开始审查 | 修改条件；说明已创建但尚未执行 |
| 排队/执行中 | 查看进度 | 后端可持续任务允许离开；展示返回查看入口；仅提供实际支持的取消能力 |
| 结果已出、待复核 | 继续处理下一项 | 显示剩余项；重新审查降为次级动作 |
| 满足完成条件 | 完成审核 | 列明未完成条件；保留现有审核/要求核验约束 |
| 已完成 | 导出交付文件 | 查看意见书、返回记录；明确导出文件包含哪些修订 |
| 正文修改导致结果失效 | 重新审查 | 常驻提示失效原因，保留原结果可查 |
| 历史版本 | 查看/导出允许的历史内容 | 明确只读及版本，提供回当前版本入口 |
| 失败或中断 | 重试/恢复 | 保留已输入资料，提供原因和可执行下一步 |

不要移除服务端对完成审核、历史只读、结果失效、导出资格的限制。UI 主动作变化不等于修改业务状态机。

意见与正文联动：点击意见定位并高亮对应段落；点击段落选中对应意见；采纳或拒绝后更新进度，并能明确撤销。验证跨页、长正文和不同视图时，用户不会失去当前处理位置。

### 5.2 模板核验：规则维护与合同检查分开表达

规则维护流程：模板列表 → 配置填写区域和规则 → 保存/试算 → 发布版本 → 返回模板列表。

合同检查流程：选择已发布模板 → 上传合同 → 执行核验 → 持久化报告 → 人工处理或继续风险审查。

规则页标题明确“模板规则配置”，同时显示模板名称、草稿/发布版本和保存状态。发布完成后给“返回模板列表”“用此版本核验合同”，后者预选对应版本。

报告展示四类业务结果：符合已配置规则、需要修改、需要人工确认、检查不完整。通过不代表合同整体无风险；检查不完整不能简单归为已明确不合规。保留原来的计算口径和范围说明。

从报告转风险审查时携带合同文件/正文引用，展示来源报告链接。如果后端尚无可靠关联字段，第一阶段用明确跳转和可恢复引用完成，不虚构永久关联能力。

### 5.3 起草：需求 → 草稿 → 送审

保留现有需求与正文编辑能力，合并重复返回按钮。为未生成需求提供草稿恢复，为正文提供“保存中 / 已保存 / 保存失败”。

“送审”先保存正文，再创建审查任务；工作台显示“来自合同草稿”并能回到该草稿。审查修改不会自动回写原草稿时，应说明生成的是独立审查任务，避免用户误以为两边同步。

新需求、修改需求、正文修改分别记录状态；自动保存失败时保留输入并提供重试。仅有未保存修改或无法安全离开时才弹确认，已保存的普通切页不反复打断。

## 6. 统一视觉与组件规范

方向：安静、清晰、适合长时间阅读的专业合同工具。入口页也采用工具产品语言，减少营销式大卡片、渐变和悬浮位移。

以下是建议的初始设计值，需要用真实页面验证，并非现状测量结论：

| 项目 | 统一建议 |
|---|---|
| 颜色 | 蓝色表示主要操作/选中；绿表示成功；橙表示待处理；红表示错误或高风险；不用绿同时表达普通功能分类 |
| 字号 | 页面标题 22–24px；区块标题 16px；常规界面 14px；辅助文字 12–13px；正文阅读区 15–16px 可调 |
| 间距 | 4/8/12/16/24/32px 阶梯；普通页面统一内容边距，工作台按阅读密度单独规定 |
| 圆角 | 输入与按钮 8px，卡片/弹窗约 12px；避免每页定义自己的圆角体系 |
| 控件 | 常规高度约 36–40px；同一行保持一致；紧凑控件用于工作台且保留清晰点击区域 |
| 主操作 | 每个主要任务区域一个突出主操作；次级操作描边/文本；危险操作使用明确危险语义 |
| 图标 | 沿用并扩充统一 SVG 图标库，逐步替换 emoji/字符图标 |
| 动效 | 保留轻微颜色/透明度反馈；减少整块上浮、旋转和所有 section 的入场动画；支持减少动效偏好 |

优先抽取：统一页头、来源返回、按钮、字段、状态标签、保存状态、列表筛选栏、分页、空状态、错误状态、确认弹窗。模型配置共用表单能力和文案，避免门户和工作台逐渐出现不同配置语义。

布局验证至少覆盖 1440×900、1366×768、1024×768。桌面三栏可拖动并恢复宽度；较窄屏幕允许左栏折叠、右栏抽屉化，中间正文优先。不要用强行缩小文字来塞下三栏。

## 7. 状态、反馈与可恢复性

- 列表的查询、状态、分页可编码到 URL；滚动和行定位放会话状态。KeepAlive 仅作为体验优化，不能成为恢复正确性的唯一依赖。
- 页面加载、按钮提交、后台运行使用不同反馈。后台任务不要长时间锁死整个界面；同步上传/创建阶段按实际能力保护离开。
- 禁用按钮附近说明原因，不只依赖 hover title；保存失败应常驻，成功通知可短暂显示。
- 空状态区分“还没有数据”“筛选无结果”“读取失败”；分别给新建、重置筛选、重试。
- 模板规则页当前原生 confirm 与其他页面自动保存策略不同，需统一为可理解的“保存并离开 / 放弃修改 / 留在当前页”；确实无法保存时解释原因。
- 弹窗验证焦点进入、焦点约束、Escape、关闭后焦点恢复；长表单错误定位到对应字段；结果不能只靠颜色表达。

## 8. 可执行改进清单

P0 指首批解决流程中断，不代表已确认数据事故。按依赖顺序实施，每批独立验收。

### 第一批：导航与恢复

- [ ] N01 将 AI 准备、模板核验准备与结果报告变成可寻址状态，兼容旧链接。
- [ ] N02 给工作台增加来源返回；无来源返回审查记录。
- [ ] N03 模板规则页增加“返回合同模板”，保留筛选与分组。

## 11. 第二轮补查：操作范围、阅读负担与结果理解

本节同样为源码审阅发现；操作定义已确认，实际误操作频率和阅读负担仍需实测。

### 11.1 筛选结果与批量操作的范围不一致（P0）

`OpinionsPanel.vue` 将批量采纳与筛选放在同一工具区域；`useTrackedReview.js` 的 acceptAllRevisions 遍历 reviewIssues，而非 filteredIssues。用户只筛出若干意见，点击“全部采纳”仍会处理本轮其他符合条件的意见。title 虽说明“本轮全部”，但不足以让作用范围始终可见。

改法：默认“采纳当前筛选的 N 项”，将“采纳本轮全部 N 项”作为独立次级动作。执行前给出范围、数量、重大风险数量和跳过原因；有待人工确认或不满足业务条件的项目继续按原规则阻止。不能只改按钮文字而不改候选集。

验收：筛出 2 项、其余 8 项隐藏时，当前筛选操作只能改变这 2 项；全量操作必须明确显示全量范围。

### 11.2 “下一处”不遵循当前筛选（P1）

`moveRevision` 和正文上方计数按 reviewIssues 全集导航，右侧展示 filteredIssues。用户选择“只看待处理”后，下一处仍可能跳到已处理或被隐藏的意见。

改法：建立明确的当前处理队列，默认按当前筛选导航；计数显示“筛选内第 2 / 5 项”。采纳后该项移出待处理队列时，定位到下一个有效项；队列为空显示“当前筛选已处理完”，而非突然跳到其他风险。

验收：正文箭头、快捷键、右侧列表采用同一队列；切换筛选后焦点和计数一致。

### 11.3 “撤销”不是用户通常理解的上一步（P0）

`undoAllReviewDecisions` 将本轮已采纳、已拒绝及待复核决定全部恢复为待处理；界面名称为“一键撤销”。另有“一键取消已采纳”，两者相邻但范围不同。现有失败回滚值得保留，但不等于用户能恢复刚被清掉的决定。

改法：明确命名“重置本轮全部处理决定”“撤回本轮已采纳修订”，放到更多操作，显示影响数量。真正的“撤销上一步”如需提供，应记录可恢复的操作快照；未实现前不要使用该承诺。重置前提供明确确认，普通单条可逆操作无需反复确认。

验收：混有采纳、拒绝和待复核时，重置与仅撤回采纳的结果分别符合描述；操作失败保留原决定。

### 11.4 批量处理存在部分成功，但反馈缺少整体结果（P1）

批量采纳逐项调用 setReviewDecision，遇到失败立即返回；之前已成功的项目仍然生效。当前有单项错误，但批次不提供完整的成功、失败和未执行汇总。

改法：显示“已完成 3 / 10，1 项失败，6 项未执行”，给出失败原因和继续处理入口；重试只处理剩余有效候选。不要显示失败就让用户误以为全部回滚，也不要宣称原子批次。批次运行中统一控制按钮状态，避免重复触发。

### 11.5 “低风险”命名比实际筛选条件更强（P1）

pendingLowRiskCount / acceptLowRiskRevisions 以 severity !== critical 选择候选，因此包括“一般风险”等非重大项，并不等同于已验证安全的低风险修改。界面按钮写“仅采纳低风险”，title 则说明一般与优化建议。

改法：改为准确的“批量采纳非重大风险建议”，或明确仅纳入哪些等级；需要人工确认、无法定位等约束单独判断。不要用风险等级暗示可以免于审阅。

### 11.6 原稿、建议稿、采纳稿之间的比较对象不够显眼（P1）

`RevisionRibbon.vue` 的“前后对比”实际描述为“原文和全部建议”，而“当前采纳稿”只合入已采纳修改。用户容易把“后”理解成自己已经接受的版本。

改法：命名为“原稿 ↔ 全部建议稿”，并在对比区两侧常驻标注；需要核对已采纳内容时提供明确的“原稿 ↔ 当前采纳稿”入口或等效视图。顶部区分“第几次审查”“第几版建议”和“当前采纳稿”，不要笼统都叫版本。

验收：只采纳 2 / 10 项时，用户能明确区分全部建议与实际交付内容；预览、导出说明和实际文件一致。

### 11.7 意见卡片重复内容多，依据层级过深（P2）

`OpinionsPanel.vue` 已在卡片直接展示标题和分析，展开“风险说明与依据”后又展示相同标题与分析；法律依据和谈判策略在下一层 details 内。`RevisionActions.vue` 同时展示原文与建议全文，中间正文也显示修订。长条款容易使单条卡片占据大量空间。

改法：卡片默认突出“问题一句话 + 风险/处理状态 + 修改摘要 + 处理按钮”；选中后展示完整建议与证据。取消重复分析，证据与依据最多一层展开；需要原文对照时联动中间文档。不要将所有解释都隐藏到无法发现的菜单。

验收：用真实长条款与数十条意见测试，逐条复核不需要反复展开两层说明和大幅滚动。

### 11.8 通过字段不可检查，统计难以追溯（P1）

`TemplateCheckReport.vue` 通过 fields.filter(status !== 'pass') 仅提供非通过字段列表，却同时展示“字段通过”统计。用户看到“通过 20 项”，不能在该组件中检查具体通过哪些值。

改法：默认保留“需处理项”，增加“全部字段 / 已通过”筛选，并展示规则、提取值及可定位证据；统计数字可跳转对应范围。为不完整检查同时突出覆盖范围，避免“无未通过项”等同于“全部检查完整”。

### 11.9 把“已处理”与“风险已解决”明确分开（P1）

`SummaryPanel.vue` 将已采纳和已拒绝都计入已处理，作为流程进度本身合理；但旁边仍是风险分布，用户可能把进度达到 100% 理解为风险全部消除。

改法：保留“已处理”口径，并补充已采纳、未采纳、待复核的分布；对保留原文的高风险意见，在交付摘要中明确“已评估但未修改”。不要简单用绿色完成状态覆盖仍存在的风险，也不要强迫全部采纳才允许完成。

### 11.10 产品承诺应与实际能力匹配（P1）

入口使用“AI 智能全面审查”，但系统支持模型不可用时的结构检查/规则回退，且存在未覆盖、待确认与历史结果失效。现有概览已承载部分说明，应保留并提高关键限制的可见性。

改法：入口可叫“合同风险审查”，提交前显示本次可用能力；结果顶部用真实数据说明执行方式、检查范围和待人工事项。未知覆盖范围写“未统计”，不要生成虚假的覆盖率或精确可信度。完成指流程完成，不代表合同无风险。
